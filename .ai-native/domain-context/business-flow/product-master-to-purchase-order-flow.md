# MVP 業務フロー: 商品マスタ登録 → 発注書作成 → 発注書出力

> **出典:** Phase 0 ヒアリング（依頼者・スポンサーロール）
> **位置づけ:** MVP スコープの AS-IS 業務フロー。 詳細運用は実ユーザ（生産管理部）への Phase 1 以降のヒアリングで補完予定。
> **最終更新:** Phase 0 ヒアリング完了時点（運用詳細の一部はスポンサーの把握外）
> **状態:** ①〜③ すべて中程度の解像度。理想の姿は未着手。

---

## 0. スコープ全体像

```
[取引先]                                          [自社]                                     [工場/仕入先]
  │                                                                                         
  │ 依頼（Excel/CSV 仕様）                                                                   
  ├──────────────────────────────►   [生産管理部/課]                                          
                                       │                                                    
                                       │  ① 商品マスタ登録 ─┐                               
                                       │                  │ ほぼ同時実行                  
                                       │  ② 発注書作成   ─┘                               
                                       │   ↓                                                
                                       │  ③ 発注書出力 (Excel)                              
                                       │                                                    
                                       ├──────────────────────────────►  [工場/仕入先]       
                                                                                            
```

**MVP 対象:** ①〜③ の3ステージ
**MVP 対象外:** 見積プロセス、受注、出荷、在庫管理、売上集計、その他（具体内容は将来ヒアリング）

> **重要:** ユーザは「MVP は3ステージで進められるが、業務全体としては他にもステージがある」と発言。MVP 完了後に追加スコープを再ヒアリングする想定。

> **重要なフロー特性:** ①と②は **ほぼ同時に実行される**。UX 設計は「商品マスタ管理画面」と「発注書管理画面」を分離するより、「**新規依頼処理ウィザード**」を起点に登録→発注を1動線で進める方が業務実態に合う。ただし「過去品番を再利用した新規発注」もあるため、既存品番選択パスも必要。

## 1. ① 商品マスタ登録

### 1.1 トリガー

**取引先からの個別依頼**（OEM/ODM の B2B 個別オーダー、Make-to-Order）。
- 季節商品の一斉投入ではなく、**都度発生**
- 受領した依頼内容に応じて品番（11桁 SKU）を新規生成

### 1.2 アクター

**生産管理部 / 課**
- 営業ではない（生産管理が責任を持つ）
- 個別オペレータが手作業で登録

### 1.3 ボリューム・粒度

| 単位 | 値 |
|------|-----|
| 1セッション = | 1企画（商品ファミリー）|
| 1企画に含まれる SKU 数 | 色 × サイズの組み合わせ分（複数）|
| 頻度 | 都度（依頼が来るたび）|
| 同時並行登録 | なし（1企画ずつ個別） |

**設計上の含意:** 2層モデル（親=企画 / 子=11桁 SKU）が業務実態と一致。色 × サイズの一括展開 UI（既存システムの F9「サイズ展開」相当）は **MVP 必須機能**。

### 1.4 入力ソース

**取引先からの Excel/CSV ファイル** が主。
- 手作業で内容を商品マスタ画面に転記している現状
- 将来的に Excel 取り込みの自動化余地あり（MVP 範囲外）

### 1.5 取引先との紐付け

商品マスタ登録時には **取引先情報を紐付けない**。
- 商品マスタは **取引先非依存のカタログ資産**
- 「最初の依頼元」のトレースは発注書履歴経由
- 同じ品番を他取引先にも展開可能な設計

### 1.6 工場・仕入単価との関係（重要）

商品マスタは **マルチ仕入先対応**:
- 1品番に対して **複数の (仕入先, 仕入単価) ペア** を保持
- 既存「品番台帳入力」画面のグリッド（仕入先・為替レート・仕入単価・仕入単価決定日 等）がこの実体
- 発注時は、複数仕入先候補の中から1つを選択し、その仕入単価を使用

### 1.7 出力（次工程への引き渡し）

- 11桁の品番（SKU）レコード × N件
- 企画親レコード × 1件
- 色明細・サイズ明細
- 価格情報（マルチ仕入先対応）

これらが ② 発注書作成のソースとなる。

### 1.8 承認・事前準備・システム外作業

**不明**（依頼者・スポンサーレベルでは把握していない）。
→ 実ユーザ（生産管理部）への Phase 1 以降のヒアリングで以下を確認する必要あり:
- 登録前の Excel 下書き有無
- 責任者承認フローの有無
- 重複品番・コード衝突の発生頻度と対処
- システム外で管理している補助情報

### 1.9 ペインポイント

**未特定**（依頼者からは具体回答得られず）。
→ 実ユーザ調査で以下の観点をヒアリング:
- 色 × サイズ展開の手間
- 品番衝突
- マスタ間整合性
- 価格・コスト計算の複雑さ
- 取引先 Excel と画面入力フォーマットの差

## 2. ② 発注書作成

### 2.1 トリガー

**商品マスタ登録と、ほぼ同時に発注**。
- 受注確定型でも在庫補充型でもない
- 依頼受領 → 商品マスタ登録 → 即発注 の一連の流れ

### 2.2 アクター

**生産管理部 / 課**（①と同じ担当者）

### 2.3 単位・粒度

| 項目 | 値 |
|------|-----|
| 1発注書の単位 | **1依頼 = 1発注書**（1発注書に複数品番を含む） |
| 1発注書の品番数 | 1企画分の SKU 全件（色 × サイズ分） |
| 集約ロジック | なし（依頼単位） |

### 2.4 発注先（仕入先/工場）の決定

**発注タイミングで都度選択**:
- 商品マスタには複数仕入先の単価がペアで保持されている（§1.6）
- その中から1つを選択し、そこへ発注
- 同じ品番でも発注ごとに異なる工場へ振り分け可能

### 2.5 数量・納期の決定

**取引先依頼をそのまま転記**:
- 取引先からの Excel/CSV に書かれた数量・納期をそのまま発注書へ転記
- バッファ・ロット調整は行わない（MTO パススルー）

### 2.6 仕入単価の決定

**商品マスタの (品番 × 仕入先) ペアから自動引き当て**:
- 選択した仕入先に対応する単価が自動セットされる
- 発注時の交渉・調整は基本なし（マスタの値を信頼）

### 2.7 取引先 vs 納品先

| 役割 | 内容 | 例 |
|------|------|------|
| 取引先 | 依頼を出した会社（請求先） | しまむら本社 |
| 納品先 | 物理的に商品が届く拠点 | しまむらセンター（物流拠点） |

両者は **概念的に別物**（取引先 ≠ 納品先）だが、データ管理上は **両方とも既存の `delivery_destination` マスタを参照**（取引先マスタは新設しない）。
1レコードが取引先・納品先の両ロールで参照される構造。

### 2.8 連絡文書テンプレート

17マスタの以下3件が発注書に含まれる:
- `document_template_purchase` (発注書定型本文)
- `document_template_confirmation` (確認表本文)
- `document_text_purchase` (動的条項、例: TT送金)

`standard_print_flag` で自動プリポピュレートされるテンプレートが決まる。

### 2.9 承認フロー

**承認なし、担当者判断で送付**:
- シンプルな1段階フロー
- ワークフロー機能は MVP に不要

### 2.10 ペインポイント

未ヒアリング。実ユーザ調査で確認予定。

## 3. ③ 発注書出力

### 3.1 出力形式

**MVP: Excel 形式**:
- 一次目標は Excel 出力
- PDF 出力は将来の追加可能性として認識

> **設計上の含意:** Excel テンプレートエンジン（例: ExcelJS, openpyxl, NPOI 等）を採用。テンプレートシート + データ流し込み方式で実装が一般的。

### 3.2 送付経路

未ヒアリング。担当者がメール添付/手渡しなど、フローは現場担当者判断と推測。

### 3.3 改訂・再発行

**発注番号に枝番を生成して上書き保存**（既存システム踏襲）:
- PO 番号は `{base_number}-{branch}` 形式
- 修正のたびに新しい枝番を生成
- 過去版は保持しない（上書き保存）

> **設計上の論点:** 「上書き保存」と「枝番ごとの版管理」は本来矛盾する。実際の運用が以下のどちらかは要確認:
> - (A) 枝番ごとに別レコードで保持 → 最新枝番が canonical
> - (B) 1レコードを枝番付与で上書き → 過去版はロスト
>
> 監査要件次第で版履歴保持の必要性が変わるため、実ユーザ調査で確認する。

### 3.4 アーカイブ・履歴管理

未ヒアリング。

## 4. データモデルの骨格（Phase 1 への申し送り）

```
┌─────────────────────────────────────────────────────────────┐
│ マスタ層（既存 17マスタ + 工場 + 甲皮素材）                       │
│                                                              │
│  size, brand, function, country, supplier,                  │
│  department, product_type, product_season, product_group,    │
│  color, material, material_classification,                   │
│  warehouse, delivery_destination,                           │
│  document_template_purchase, document_template_confirmation, │
│  document_text_purchase                                      │
│                                                              │
│  [追加必須] factory(工場), upper_material(甲皮素材)            │
└─────────────────────────────────────────────────────────────┘
            │
            ▼
┌─────────────────────────────────────────────────────────────┐
│ 商品層（2階層）                                                │
│                                                              │
│  product_family (企画親)                                    │
│    ├ product (11桁 SKU)                                     │
│    │   └ product_supplier_price (品番×仕入先→単価)           │
│    ├ product_color (色明細)                                 │
│    └ product_size (サイズ明細)                              │
└─────────────────────────────────────────────────────────────┘
            │
            ▼
┌─────────────────────────────────────────────────────────────┐
│ 発注層                                                       │
│                                                              │
│  purchase_order (1依頼=1発注書、枝番管理)                     │
│    ├ purchase_order_line (品番×数量、N件)                   │
│    ├ 取引先 FK → delivery_destination                       │
│    ├ 納品先 FK → delivery_destination                       │
│    ├ 仕入先 FK → supplier                                   │
│    └ テンプレート選択 → document_template_*                 │
└─────────────────────────────────────────────────────────────┘
            │
            ▼ Excel 出力（MVP）/ PDF 出力（将来）
```

## 5. 設計上の重要な発見（Phase 1 への申し送り）

| # | 発見 | 設計影響 |
|---|------|----------|
| 1 | 2層モデル（企画親 + SKU子）が業務実態と一致 | テーブル設計を `product_family` + `product` の親子構造に |
| 2 | F9「サイズ展開」は MVP 必須 | UI 設計に色 × サイズマトリクス一括登録機能を組み込む |
| 3 | 商品マスタは取引先・仕入先 ともに非依存 | 商品マスタテーブルに取引先 FK を持たせない。マルチ仕入先は専用サブテーブル `product_supplier_price` |
| 4 | 取引先依頼の Excel/CSV 形式が主 | Phase 2 以降で Excel 取り込み機能を検討（MVP は手入力） |
| 5 | 業務全体は3ステージより広い | MVP 完了後の追加スコープに備え、データモデルは拡張容易性を意識 |
| 6 | スポンサーは運用詳細を把握していない | 実ユーザ（生産管理部）へのヒアリングを Phase 1 以降で必須化 |
| 7 | ①と②はほぼ同時実行 | 「新規依頼処理ウィザード」を主動線にする UX。「過去品番再利用パス」も併設 |
| 8 | 取引先マスタを新設せず、納品先マスタを兼用 | `delivery_destination` を取引先・納品先の両ロールで参照。役割識別子は PO の FK 名で吸収 |
| 9 | 発注書は Excel 出力（MVP）、PDF は将来 | Excel テンプレートエンジン採用。テンプレートシート + データ流し込み |
| 10 | 改訂は枝番管理（過去版保持の運用は要確認） | PO 番号は `{base}-{branch}` 形式。版履歴の物理保持要否は実ユーザ調査で確定 |
| 11 | 承認フローなし | ワークフロー機能不要、シンプルな保存→出力フローで OK |
| 12 | MTO パススルー（数量・納期は依頼転記） | 在庫・キャパシティ計算ロジック不要 |
