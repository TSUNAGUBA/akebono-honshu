# MVP 業務フロー: 商品マスタ登録 → 発注書作成 → 発注書出力

> **出典:** Phase 0 ヒアリング（依頼者・スポンサーロール）+ 既存画面スクリーンショット5枚（品番台帳入力 / 発注書作成【国内用】/ 発注書作成【海外用】×2 / 発注書出力【海外用】）の分析
> **位置づけ:** MVP スコープの AS-IS 業務フロー。 詳細運用は実ユーザ（生産管理部）への Phase 1 以降のヒアリングで補完予定。
> **最終更新:** Phase 0 ヒアリング完了時点
> **状態:** ①〜③ すべて中〜高解像度。理想の姿は仮説状態。

---

## 0. スコープ全体像

```
[取引先]                                          [自社]                                     [工場/仕入先]
  │                                                                                         
  │ 依頼（Excel/CSV 仕様）                                                                   
  ├──────────────────────────────►   [生産管理部/課]                                          
                                       │                                                    
                                       │  ① 商品マスタ登録 ─┐                               
                                       │                  │ ほぼ同時実行                  
                                       │  ② 発注書作成   ─┘                               
                                       │   ↓                                                
                                       │  ③ 発注書出力 (Excel)                              
                                       │                                                    
                                       ├──────────────────────────────►  [工場/仕入先]       
                                                                                            
```

**MVP 対象:** ①〜③ の3ステージ、**国内発注フローのみ**
**MVP 対象外:** 見積プロセス、受注、出荷、在庫管理、売上集計、**海外発注フロー**（後回し）、その他

> **重要1:** ユーザは「MVP は3ステージで進められるが、業務全体としては他にもステージがある」と発言。MVP 完了後に追加スコープを再ヒアリングする想定。

> **重要2:** ①と②は **ほぼ同時に実行される**。UX 設計は「商品マスタ管理画面」と「発注書管理画面」を分離するより、「**新規依頼処理ウィザード**」を起点に登録→発注を1動線で進める方が業務実態に合う。ただし「過去品番を再利用した新規発注」もあるため、既存品番選択パスも必要。

> **重要3:** 海外発注は MVP 対象外だが、データモデル設計時には海外特有の項目（4ロール構造・複数倉庫・複数日付・週次出荷スケジュール）の拡張余地を確保する。

## 1. ① 商品マスタ登録

### 1.1 トリガー

**取引先からの個別依頼**（OEM/ODM の B2B 個別オーダー、Make-to-Order）。
- 季節商品の一斉投入ではなく、**都度発生**
- 受領した依頼内容に応じて品番（11桁 SKU）を新規生成

### 1.2 アクター

**生産管理部 / 課**
- 営業ではない（生産管理が責任を持つ）
- 個別オペレータが手作業で登録

### 1.3 ボリューム・粒度

| 単位 | 値 |
|------|-----|
| 1セッション = | 1企画（商品ファミリー）|
| 1企画に含まれる SKU 数 | 色 × サイズの組み合わせ分（複数）|
| 頻度 | 都度（依頼が来るたび）|
| 同時並行登録 | なし（1企画ずつ個別） |

**設計上の含意:** 2層モデル（親=企画 / 子=11桁 SKU）が業務実態と一致。色 × サイズの一括展開 UI（既存システムの F9「サイズ展開」相当）は **MVP 必須機能**。

### 1.4 入力ソース

**取引先からの Excel/CSV ファイル** が主。手作業転記の現状。将来的に Excel 取り込み自動化の余地あり（MVP 範囲外）。

### 1.5 取引先との紐付け

商品マスタ登録時には **取引先情報を紐付けない**（取引先非依存のカタログ資産）。
最初の依頼元のトレースは発注書履歴経由。

### 1.6 工場・仕入単価との関係

商品マスタは **マルチ仕入先対応**:
- **1アイテム（product_family、企画単位）に対して** 複数の (仕入先, 仕入単価) ペアを保持
- 色違い・サイズ違いの SKU はすべて同一の仕入単価（**Phase 6 で業務ルール明示化**）
- 既存画面のグリッド（仕入先・為替レート・仕入単価・仕入単価決定日 等）がこの実体
- 発注時は、複数仕入先候補の中から1つを選択し、その仕入単価を使用

### 1.7 出力（次工程への引き渡し）

- 11桁の品番（SKU）レコード × N件
- 企画親レコード × 1件
- 色明細・サイズ明細
- 価格情報（マルチ仕入先対応）

### 1.8 承認・事前準備・システム外作業

**不明**（依頼者・スポンサーレベルでは把握していない）。Phase 1 以降の実ユーザヒアリングで補完。

### 1.9 ペインポイント

**未特定**。Phase 1 以降で実ユーザに確認。

## 2. ② 発注書作成（MVP: 国内用）

### 2.1 トリガー

**商品マスタ登録と、ほぼ同時に発注**。依頼受領 → 商品マスタ登録 → 即発注 の連続フロー。

### 2.2 アクター

**生産管理部 / 課**（①と同じ担当者）。

### 2.3 単位・粒度

| 項目 | 値 |
|------|-----|
| 1発注書の単位 | **1依頼 = 1発注書**（1発注書に複数品番を含む） |
| 1発注書の品番数 | 1企画分の SKU 全件（色 × サイズ分） |

### 2.4 国内発注画面の項目構成（観察ベース）

#### 2.4.1 ヘッダ項目

| 項目 | データソース | 備考 |
|------|------------|------|
| 処理 | 1新規 / 2修正 / 3参照 | コンボボックス |
| ユーザ名 | ログインユーザ表示 | 例: 古川智惠 |
| 最終更新者 / 最終更新日 | システム自動 | |
| 作成管理番号 | システム採番 | 例: 25-00411（年2桁-連番5桁）|
| 状態 | ステータス | 例: 正式発注書 |
| 発注先 | `supplier` マスタ（仕入先/工場） | 例: 001 ㈱アスカ, 005 ㈱MSP, 035 小澤重㈱ |
| 納品先 | `delivery_destination` マスタ | 例: しまむらセンター, KEYUCA商品センター |
| 取引先納入日 | 日付入力 | YY/MM/DD |
| 発注事業部 | `department` マスタ | 例: 001 第1事業部 |
| 発注担当者 | **`user` マスタ（17マスタ未記載・追加必須）** | 例: 008 佐藤浩始 |
| 発注者・副1〜副6 | `user` マスタ（最大6人） | 副担当者 |
| 発注管理者 | `user` マスタ | 監督者 |
| 納入倉庫1 | `warehouse` マスタ | 国内は1拠点のみ |
| 発注情報作成日 | システム自動 | |

#### 2.4.2 明細グリッド

| 列 | 内容 |
|----|------|
| No | 行番号 |
| 品番 | 11桁 SKU |
| 色 / サイズ | マスタ参照 |
| 仮番号 | 暫定品番（品番確定前） |
| 品名 | 商品名 |
| 倉庫1（入数 / 発注数） | 倉庫別の入数と発注数 |
| 見積単価 / 仕入単価 | 単価 |
| 備考 | 自由記述 |

#### 2.4.3 機能ボタン

| キー | 機能 |
|------|------|
| F1 | コード検索 |
| F2 | 履歴照会 |
| F3 | 削除 |
| F5 | 明細行削除 |
| F6 | 生産確認書 |
| F7 | 発注書 |
| F10 | 登録 |
| F11 | クリア |
| F12 | 閉じる |

### 2.5 発注先（仕入先/工場）の決定

**発注タイミングで都度選択**:
- 商品マスタには複数仕入先の単価がペアで保持されている（§1.6）
- その中から1つを選択し、そこへ発注

### 2.6 数量・納期の決定

**取引先依頼をそのまま転記**（MTO パススルー）。

### 2.7 仕入単価の決定

**商品マスタの (品番 × 仕入先) ペアから自動引き当て**。

### 2.8 取引先 vs 納品先の整理（重要・前回判断を更新）

> **更新理由:** 国内画面のみ見ると「発注先（=supplier） + 納品先」の2項目だが、海外画面を見ると「発注先 + 荷揚地 + **得意先** + 納品先」の4項目構造。MVP は国内のみだが、データモデルは将来海外対応のため4ロール構造を念頭に置く。

| 役割 | 業務上の意味 | 参照マスタ | 国内 | 海外 |
|------|-------------|-----------|------|------|
| 発注先 | 発注を出す先（仕入先/工場） | `supplier` | ✅ | ✅ |
| 荷揚地 | 海外輸送の港 | （海外用、未定） | - | ✅ |
| 得意先 | 注文を出した会社（請求先） | （要設計） | （暗黙） | ✅ 明示 |
| 納品先 | 物理的に商品が届く拠点 | `delivery_destination` | ✅ | ✅ |

**MVP 設計判断:** 国内では「得意先」を画面で明示しないが、データモデルには「customer」属性を持たせて将来海外対応に備える（NULL 許容で導入）。スポンサー回答「取引先を納品先マスタに含める」は **国内画面範囲では成立** するが、海外対応時に再考必要。

### 2.9 連絡文書テンプレート

17マスタの以下3件が発注書/管理表に紐付:
- `document_template_purchase` (発注書定型本文)
- `document_template_confirmation` (確認表本文)
- `document_text_purchase` (動的条項)

`standard_print_flag` で自動プリポピュレートされるテンプレートが決まる。

### 2.10 承認フロー

**承認なし、担当者判断で送付**（シンプル1段階フロー）。

### 2.11 ペインポイント

未ヒアリング。Phase 1 以降で実ユーザに確認。

### 2.12 海外フローとの差分（参考、MVP 対象外）

海外画面で観察された追加項目（MVP では実装しないが、データモデル拡張余地として記録）:

| 項目 | 内容 |
|------|------|
| 荷揚地 | 海外港の指定（例: 香港） |
| 得意先 | 取引先と別フィールド（例: 流通方式XO姉妹） |
| 納入倉庫2 / 倉庫3 | 1発注で3拠点に分割可能 |
| 工場出荷日 | 工場が商品を出す日 |
| 商品用出荷日 | 商品の出荷日 |
| 海外出荷日 | 海上輸送の出荷日 |
| **週次出荷スケジュール** | グリッドの列ヘッダが日付（例: 4/10, 4/17, 4/24, 5/1, 5/8）で、品番ごとに週次の数量を分割入力。1発注を複数納期に分割して送る仕組み |
| サンプル合格 / 版権 / アソート箱 | 品番ごとのチェック列 |

## 3. ③ 発注書出力（MVP: 国内用）

### 3.1 出力形式

**MVP: Excel 形式**。PDF は将来追加の可能性。

> **設計上の含意:** Excel テンプレートエンジン（例: ExcelJS, openpyxl, NPOI 等）を採用。テンプレートシート + データ流し込み方式で実装が一般的。

### 3.2 出力画面の項目構成（観察ベース、海外用画面より、国内も同様の構造と推測）

#### 3.2.1 ヘッダ項目

| 項目 | 内容 |
|------|------|
| 作成管理番号 | 例: 26-00090 |
| 発注中止 | チェックボックス（発注書単位のキャンセル） |
| 発注日 | 例: 260318 |
| 出荷指示番号 | （別の番号系） |
| 発注番号 | 例: S3858（出力時に採番される正式番号） |
| 得意先印字なし / 納品先印字なし | チェックボックス（印字制御） |

> **3種類の番号体系:** `作成管理番号`（編集中ID）/ `発注番号`（出力時の正式ID, S始まり）/ `出荷指示番号`（後続の出荷フロー用）。

#### 3.2.2 連絡文章（発注書本文用、最大6行）

各行に `document_text_purchase` マスタから「一覧から複写」ボタンで動的選択。
`standard_print_flag = 1` のものは「標準印字取込」ボタンで一括投入。

例（海外用）:
- 01 値札, ヘッダーを付けて出荷してください。
- 02 値札, 証紙等の副資材に関しては発注数×5%にて発注していますのでご留意ください。

#### 3.2.3 登録文章（管理表用、最大4行）

事前マスタ（`document_template_confirmation` 相当）から選択。

例:
- 001 サンプル合格と単価は、企画者と工場出荷日の2週間前迄に済ませる。
- 002 ブランドシールはホンシュで手配...
- 003 監修用(990)は、工場で検品した良品を本社に送ってください。
- 004 未合格、単価未決定でも、日本の責任で生地発注。

#### 3.2.4 出力帳票選択

ラジオボタン:
- ⦿ 発注書のみ
- ○ 管理表のみ
- ○ 発注書 + 管理表

→ **MVP は「発注書」だけで OK か、「管理表」も実装するかは要判断**（実ユーザヒアリング項目）。

#### 3.2.5 機能ボタン

F9 登録 / F10 出力 / F11 クリア / F12 閉じる

### 3.3 編集・再出力

> **Phase 6 で確定:** 状態モデルを Active / Cancelled の 2 値に簡素化。発注書の「編集」と「Excel 出力」は分離した独立操作。

- **編集:** `status=Active` の発注書はいつでも編集可能。改訂用枝番管理は **廃止**（旧設計の `Snnnn-NN` 形式の枝番採番は MVP では実装しない）
- **再出力:** Excel はいつでも何度でも出力可能。初回出力時のみ発注番号 `Snnnn` を採番 + `first_exported_at` を記録
- **業務可視化:** UI 上で「未出力（仕入先未送付）」「初回出力済 YYYY-MM-DD」のバッジで業務状態を可視化
- **編集履歴:** 監査ログ（audit_logs）に蓄積、UI でも参照可能

### 3.4 アーカイブ・履歴管理

未ヒアリング。

## 5. 設計上の重要な発見（Phase 1 への申し送り）

| # | 発見 | 設計影響 |
|---|------|----------|
| 1 | 2層モデル（企画親 + SKU子）が業務実態と一致 | `product_family` + `product` の親子構造 |
| 2 | F9「サイズ展開」は MVP 必須 | 色 × サイズマトリクス一括登録機能 |
| 3 | 商品マスタは取引先・仕入先 ともに非依存 | マルチ仕入先は専用サブテーブル |
| 4 | 取引先依頼の Excel/CSV 形式が主 | Phase 2 以降で Excel 取り込み機能 |
| 5 | 業務全体は3ステージより広い | データモデルは拡張容易性を意識 |
| 6 | スポンサーは運用詳細を把握していない | Phase 1 で実ユーザ（生産管理部）ヒアリング必須 |
| 7 | ①と②はほぼ同時実行 | 「新規依頼処理ウィザード」を主動線 |
| 8 | **海外画面で4ロール構造（発注先/荷揚地/得意先/納品先）が明示** | MVP は2ロール（発注先+納品先）だが、`customer` 等は将来拡張で追加 |
| 9 | 発注書は Excel 出力（MVP）、PDF は将来 | Excel テンプレートエンジン採用 |
| 10 | 改訂は枝番管理 | PO 番号は `{base}-{branch}` 形式。物理保持要否は要確認 |

## 6. 理想の姿（仮説）

> **重要:** 以下は依頼者・スポンサーの **直感に基づく仮説** であり、生産管理部からの確認されたペインではない。MVP では過剰投資せず、設計哲学として保持。Phase 2 のプロトタイプで実ユーザに当てて反応を見る。

**設計哲学（仮説）:** **「速度・自動化」より「正しさ・誤入力防止」を優先**
- バリデーション中心の UX（入力時即時チェック、確認サマリ、確認ダイアログ）
- 間違えにくい入力導線（プルダウン中心、必須項目の視認性、誤組み合わせ拒否）
- 重複・矛盾の自動検知（品番衝突、色×サイズ整合性、価格未入力）
- 証跡・トレーサビリティ（誰が何をいつ入力・変更したか）

**未成熟イメージ（Something else）:** スポンサーが明確に言語化できない領域。Phase 1 以降で仮説を提示しながら探る。
