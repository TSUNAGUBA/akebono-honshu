# プロジェクトスポンサー（依頼者）ペルソナ

> **注意:** 本ドキュメントは **エンドユーザ** ではなく **プロジェクトの依頼者・スポンサー** のプロファイルである。
> 実際のシステム利用者（生産管理部担当）のペルソナは Phase 1 以降のヒアリングで別途作成する。

---

## 1. ロール

**プロジェクト依頼者 / スポンサー（業務知見の代理提供者）**

- リプレース対象システムの **発注主**
- 業務全体の把握者・意思決定者
- AI ネイティブ開発方法論における Phase 0 ヒアリングの主たる対話相手

---

## 2. 知見範囲のマッピング

各領域での解像度を明示することで、回答の信頼度を判断する基準とする。

| 領域 | 解像度 | 補足 |
|------|--------|------|
| 業界・事業内容 | ◎ | フットウェア + ホームウェアの OEM/ODM 卸という事業構造を明確に説明可能 |
| MVP スコープ判定 | ◎ | 「3ステージで進める」「国内のみ」等の方針判断を即決できる |
| 17マスタの正規仕様 | ◎ | 既存システムから抽出された英語スペックを提供可能 |
| 品番（11桁 SKU）の体系 | ◎ | Excel コード変換表を提供、各桁の意味を即答可能 |
| 既存システムの画面構造 | ○ | 主要画面のスクリーンショットを提供可能 |
| 高レベル業務フロー | ○ | 3ステージの順序、トリガー、アクター部署、概略単位を把握 |
| 業務フローの運用詳細 | △ | 例: 承認フロー有無、Excel 下書き運用は「不明」と明言 |
| 現場の具体的ペインポイント | ✗ | 「現状発生しているとは聞いていない」「自分が勝手にあると良いと思っただけ」 |
| 数値（取引件数、エラー率等） | ✗ | 言及なし |

> **重要:** 「不明」「聞いていない」と率直に答えてくれる **誠実な対話者**。これは大きな価値で、推測や創作的回答による誤導リスクが低い。

---

## 3. 意思決定スタイル

| 観点 | 特徴 |
|------|------|
| 反応速度 | 速い。選択肢を提示すると即決する |
| 抽象度許容 | 中程度。「未成熟イメージ」のような曖昧領域も率直に提示してくる |
| 情報提供 | プロアクティブ。「画面の画像があります、必要ですか？」のように追加情報を能動的に申し出る |
| 誠実性 | 高い。確信のない領域は「不明」と明言する |
| 推測許容度 | 仮説や推論を歓迎するが、自身は仮説と確定を区別する |

---

## 4. 委任境界（このユーザに聞くべきでない領域）

以下は本スポンサーへの追加質問では解消しないため、実ユーザ（生産管理部）への直接ヒアリングが必要:

- **承認フロー・運用ルール**: 部門内の業務ルール、未文書化の慣習
- **ペインポイント・改善要望**: 現場担当者が日々感じている具体的不満
- **エラー・例外処理の頻度**: 実際のミス発生状況
- **業務ボリューム数値**: 日次/月次の取引件数、繁忙期
- **画面操作の具体的フロー**: クリック順序、よく使うショートカット
- **管理表の使われ方**: 出力後どう活用されているか
- **副担当者（副1〜6）の運用ルール**: 誰がどう使い分けているか

## 5. 本スポンサーから得られた重要な発言（一次資料）

| 発言 | 含意 |
|------|------|
| 「MVP では3ステージ以外もあるが、一旦この3ステージで進めることは可能ですか？」 | 全体業務は3ステージより広いが、MVP スコープを絞る判断を明示 |
| 「品番作成時には紐付せず、発注書作成時に紐付」 | 商品マスタは取引先非依存というデータ設計を確定 |
| 「商品マスタの仕入単価をそのまま使用」+「品番×工場で複数仕入単価を保持」 | マルチ仕入先サブテーブルの存在を確定 |
| 「承認なし、担当者判断で送付」 | ワークフロー機能不要を確定 |
| 「現状発生しているとは聞いていません。ただあると良いと私が勝手に思っただけです。」 | 「誤入力防止」は仮説扱いで MVP 過剰投資を避ける判断材料 |
| 「現時点では語りにくい未成熟イメージ」 | Phase 1 以降で仮説提示型の探索を許容する姿勢 |
| 「国内だけ MVP、海外は後回し」 | スコープ絞り込みを即決 |

## 6. 本ペルソナの取り扱い指針（AI ロール起動時）

新規セッションで本プロジェクトのスポンサーと対話する際の指針:

1. **抽象的質問は具体的選択肢に変換して提示する** — このスポンサーは選択肢があると速く決定できる
2. **「不明」回答を受け入れる** — 知らない領域を無理に推測させない。実ユーザ確認事項として記録する
3. **仮説と確定を明確に区別する** — 確定事項は「確認済み」、推測は「仮説」とラベル付けする
4. **追加情報提供の打診に応じる** — 「画像/資料あります」の申し出には積極的に受領する
5. **MVP スコープ判定を率直に問う** — 「これは MVP に含めるか？」と直接質問できる相手
6. **理想の姿・ペインポイントは深追いしない** — 知見の限界があるため、実ユーザ調査を Phase 1 以降で計画する
