## 0. 共通前提

### 主アクター（ユーザロール）

| ロール | 該当 |
|--------|------|
| **オペレータ** | 生産管理部/課 の担当者。日常業務として商品マスタ登録・発注書作成・出力を行う |
| **マスタ管理者** | 同じ生産管理部内、またはシステム管理者。マスタ保守を行う（オペレータと兼務の可能性あり、要確認） |

### MVP 想定マスタ（18 件）

既存17マスタ + 追加1マスタ:
- **既存17件:** size, brand, function, country, supplier, department, product_type, product_season, product_group, color, material, material_classification, warehouse, delivery_destination, document_template_purchase, document_template_confirmation, document_text_purchase
- **追加1件:** `user`（ユーザ）— 既存「利用者マスタメンテナンス」画面で AS-IS 確認済、4権限カテゴリ × レベル分け（詳細: `domain-context/industry/honshu-master-schema.md#7`）。**2026-07-27 追記: 実装では勤怠権限 `attendance_permission` を 5 つ目のカテゴリとして追加済み**（Iteration 30、akebono-office からの勤怠移植）

**既存マスタの兼用/参照（追加マスタは作らない）:**
- `supplier` ← **工場（factory）** も一旦兼用（MVP 暫定、supplier_type で区別想定）
- `material` ← **甲皮素材（upper_material）** も参照（商品マスタ側の「甲皮/中底/底」はいずれも material.code への FK）

### 運用上の制約条件

| 項目 | 値 | 状態 |
|------|-----|------|
| 同時利用者数 | **1-2 名（シングルユーザ近似）** | ✅ 確定 |
| 利用頻度 | 都度（取引先依頼ごと） | ✅ 確認済（Phase 0） |
| 使用環境 | **Web ブラウザ（Chrome/Edge 等）** | ✅ 確定 |
| デバイス | **PC のみ（モバイル対応は Post-MVP）** | ✅ 確定 |
| 既存システムとの並行稼働 | リプレース戦略 | ⏳ Phase 3 で再検討（移行戦略と合わせて） |

## UC-1: 取引先からの新規依頼を受けて商品マスタを登録し、発注書を作成・出力する

### 基本情報

| 項目 | 内容 |
|------|------|
| ID | UC-1 |
| 名称 | 新規依頼処理（登録→発注→出力の連続フロー） |
| 主アクター | オペレータ |
| 業務上の位置付け | **MVP の主動線**。「①+②+③ ほぼ同時実行」の連続ウィザード |
| 頻度 | 都度（取引先依頼が届くたび） |

### 前提条件

- 18マスタ（既存17 + ユーザ）が整備済み
- オペレータがログイン済み
- 取引先から Excel/CSV 形式の依頼を受領済み（手元にある）

### トリガー

オペレータが「新規依頼処理」メニューを起動する。

### メインフロー（基本シナリオ）

| # | アクター操作 | システム応答 |
|---|------------|-------------|
| 1 | オペレータが「新規依頼処理」画面を開く | 新規企画作成モードで画面表示 |
| 2 | オペレータが商品タイプ・季節・機能・ブランド・甲皮素材・中底素材・底素材・商品分類をドロップダウンから選択する（甲皮素材/中底素材/底素材はいずれも `material` マスタを参照） | 各選択に応じて仮品番（11桁の上位9桁）が動的にプレビュー表示される |
| 3 | オペレータが商品名・商品名2 を入力する | 入力受付 |
| 4 | オペレータが色を複数選択する（色マスタからチェックリスト等） | 選択された色リストを表示 |
| 5 | オペレータがサイズを複数選択する（サイズマスタから） | 選択されたサイズリストを表示 |
| 6 | オペレータが「サイズ展開」ボタンを押す | 色 × サイズの組み合わせ分の SKU（11桁品番）が一括生成され、グリッドに表示される |
| 7 | オペレータが各 SKU に対し仕入先と仕入単価を入力する（1品番に複数仕入先入力可） | マルチ仕入先単価が記録される |
| 8 | オペレータが価格（正価額・小売価額・納品先価額）を入力する | 入力受付 |
| 9 | オペレータが「登録」ボタンを押す | 商品マスタが確定保存され、自動的に発注書作成画面へ遷移する |
| 10 | オペレータが発注先（仕入先/工場、いずれも `supplier` マスタを参照）をドロップダウンから選択する | 選択した仕入先に対応する仕入単価が自動で発注書側に引き当てられる |
| 11 | オペレータが納品先をドロップダウンから選択する | 選択受付 |
| 12 | オペレータが発注事業部・発注担当者（自分）・副担当者（任意）・発注管理者を選択する | 選択受付 |
| 13 | オペレータが納入倉庫1・取引先納入日を入力する | 入力受付 |
| 14 | システムが明細グリッドに UC-1 で登録した全 SKU を自動転記する | 表示 |
| 15 | オペレータが各 SKU の発注数量を入力する（取引先依頼の Excel を見ながら手動転記） | 入力受付 |
| 16 | オペレータが連絡文章を選択する（テンプレートから複写 + 標準印字取込 + 自由編集） | 選択受付 |
| 17 | オペレータが「登録」ボタンを押す | 発注書が確定保存され、**作成管理番号**（例: 26-00411）が自動採番される。発注書出力画面へ遷移 |
| 18 | オペレータが「出力帳票選択」で「発注書のみ」を選ぶ | 選択受付 |
| 19 | オペレータが「出力」ボタンを押す | **発注番号**（例: S3858）が自動採番され、Excel ファイルが生成・ダウンロードされる |

### 代替フロー

- **AF-1（途中保存）:** ステップ 9, 17 以外でも、オペレータが「クリア」「閉じる」を押した場合の挙動（破棄? 下書き保存?）→ **要確認**
- **AF-2（マスタ未登録）:** ステップ 2 で必要なマスタ値がない場合、マスタ管理画面への遷移を提案するか、別タブで開くか → **要確認**

### 例外フロー

- **EF-1（仮品番衝突）:** ステップ 6 で生成された 11桁品番が既存品番と衝突する → エラー表示し、連番（4-6桁目）を自動インクリメントするか、オペレータに再選択を促す → **要設計**
- **EF-2（必須項目未入力）:** ステップ 9, 17 で必須項目が未入力 → エラー表示し未入力箇所を強調

### 事後条件

- 商品マスタ（企画 + SKU + マルチ仕入先単価）が DB に保存される
- 発注書（ヘッダ + 明細 + 連絡文章）が DB に保存される
- 発注書 Excel ファイルがオペレータの手元にある（工場送付準備完了）

### システム化 vs システム外の仕分け

| 範囲 | 該当 |
|------|------|
| **システム化（MVP 対象）** | 上記メインフローのすべて。マスタ選択・自動採番・サイズ展開・マルチ仕入先紐付・Excel 出力 |
| **システム外** | 取引先 Excel の解釈（人間の判断）、Excel ファイルの工場送付（メール添付等）、依頼内容の妥当性確認 |
| **MVP 範囲外（将来）** | 取引先 Excel の自動取り込み、海外フロー、PDF 出力 |

## UC-2: 過去登録済みの品番を再利用して追加発注書を作成・出力する

### 基本情報

| 項目 | 内容 |
|------|------|
| ID | UC-2 |
| 名称 | 既存品番再利用による追加発注 |
| 主アクター | オペレータ |
| 業務上の位置付け | リピート受注時の動線。商品マスタ登録ステップをスキップ |
| 頻度 | 都度（定番品の追加発注、リピート依頼時） |

### 前提条件

- 対象品番が商品マスタに登録済み
- 取引先から追加発注の依頼を受領済み

### トリガー

オペレータが「発注書作成」画面を直接開く（新規企画を作らない）。

### メインフロー

| # | アクター操作 | システム応答 |
|---|------------|-------------|
| 1 | オペレータが「発注書作成」画面を開く | 既存品番選択モードで表示 |
| 2 | オペレータが品番検索（コード検索 or 履歴照会）を行う | 検索結果一覧を表示 |
| 3 | オペレータが対象品番を選択する（複数選択可） | 選択した品番が明細グリッドに転記される |
| 4 | オペレータが各品番の発注数量を入力する | 入力受付 |
| 5 | オペレータが発注先・納品先・倉庫・日付・担当者を選択する | 入力受付 |
| 6 | オペレータが連絡文章を選択する | 選択受付 |
| 7 | オペレータが「登録」ボタンを押す | 発注書が確定保存、作成管理番号が自動採番される |
| 8 | オペレータが「出力」ボタンを押す | 発注番号が採番され、Excel ファイルが生成される |

### システム化 vs システム外

| 範囲 | 該当 |
|------|------|
| システム化 | 品番検索（検索性・絞り込み性は要件）、明細自動転記、登録・出力 |
| システム外 | どの過去品番を選ぶかの判断（オペレータの知識） |

## UC-3: 既存発注書を改訂し、枝番付きで再出力する

### 基本情報

| 項目 | 内容 |
|------|------|
| ID | UC-3 |
| 名称 | 発注書改訂 |
| 主アクター | オペレータ |
| 業務上の位置付け | 数量・納期の変更、社内発見の誤り訂正 |
| 頻度 | 不定期（変更が発生したとき） |

### 前提条件

- 改訂対象の発注書が確定済み（既に発注番号採番済み）

### トリガー

取引先からの数量・納期変更依頼、または社内ミス発見。

### メインフロー

| # | アクター操作 | システム応答 |
|---|------------|-------------|
| 1 | オペレータが「発注書一覧」画面を開き、対象発注書を検索する | 検索結果を表示 |
| 2 | オペレータが対象を選択し「修正」モードで開く | 既存内容が編集可能状態で表示される |
| 3 | オペレータが数量・納期・連絡文章等を変更する | 入力受付 |
| 4 | オペレータが「登録」ボタンを押す | 発注番号に枝番が付与される（例: S3858-01 → S3858-02）。旧版データの保持要否は要確認 |
| 5 | オペレータが「出力」ボタンを押す | 改訂版 Excel が生成される |

### 例外フロー

- **EF-1（発注中止）:** 発注書全体をキャンセルしたい場合、「発注中止」フラグを立てる。物理削除はしない（履歴保持）

### システム化 vs システム外

| 範囲 | 該当 |
|------|------|
| システム化 | 検索・編集・枝番採番・再出力 |
| システム外 | 工場への改訂版送付、改訂理由の合意 |

## UC-4: マスタデータを保守する

### 基本情報

| 項目 | 内容 |
|------|------|
| ID | UC-4 |
| 名称 | マスタ管理（18マスタの CRUD: 既存17 + ユーザ） |
| 主アクター | マスタ管理者（オペレータと兼務可） |
| 業務上の位置付け | UC-1〜3 の前提条件を維持するための保守作業 |
| 頻度 | 不定期（新規追加・改訂時） |

### 前提条件

- マスタ管理者がログイン済み

### トリガー

新規取引先追加、新商品タイプ追加、新仕入先追加、ユーザ追加・退職、その他マスタ変更要求。

### メインフロー（代表例: 仕入先マスタ追加 ― 工場の登録もこのマスタで行う）

| # | アクター操作 | システム応答 |
|---|------------|-------------|
| 1 | マスタ管理者が「マスタ管理」メニューから「仕入先マスタ」を開く | 既存仕入先一覧を表示 |
| 2 | マスタ管理者が「新規」ボタンを押す | 新規入力フォームを表示 |
| 3 | マスタ管理者が code、name、official_name、country_code、supplier_type（仕入先/工場 等の区別）、alert_target、item_conversion_code 等を入力する | 入力受付。code の重複チェック |
| 4 | マスタ管理者が「保存」ボタンを押す | マスタが確定保存される |

### メインフロー（代表例: ユーザマスタ追加）

| # | アクター操作 | システム応答 |
|---|------------|-------------|
| 1 | マスタ管理者が「マスタ管理」メニューから「ユーザマスタ」（既存「利用者マスタメンテナンス」相当）を開く | 既存ユーザ一覧を表示 |
| 2 | マスタ管理者が「新規行」を追加する | 入力可能行が追加される |
| 3 | マスタ管理者が 社員番号、ユーザID、ユーザ名 を入力する | 社員番号の重複チェック |
| 4 | マスタ管理者が 企画担当 / 営業担当 のチェックボックスを設定する | 入力受付 |
| 5 | マスタ管理者が 4種類の権限（品番台帳/発注書作成/発注情報/工程実績）レベルを各ドロップダウンで選択する | 入力受付 |
| 6 | マスタ管理者が「更新」ボタンを押す | ユーザマスタが確定保存される (Phase 6 で F-key 廃止 F-21、画面ボタン統一 2026-05-19) |

### 代替フロー

- **AF-1（既存編集）:** 一覧から既存レコードを選択 → 編集 → 保存
- **AF-2（論理削除）:** 一覧から選択 → 「削除」チェック ON → 保存。物理削除はしない

### システム化 vs システム外

| 範囲 | 該当 |
|------|------|
| システム化 | 全マスタの CRUD、論理削除、コード重複チェック、FK 整合性チェック |
| システム外 | マスタ追加の妥当性判断（人間の意思決定）、社内承認フロー（あれば。スポンサー把握外） |

## 3. 全 UC を貫く横串の論点

### 3.1 ユーザ認証・権限

| 項目 | 状態 |
|------|------|
| ログイン方式（ID/パスワード? SSO?） | Phase 3 / Phase 4 で確定 |
| 権限分離 | **AS-IS で確認済**。既存ユーザマスタに4権限カテゴリ × レベル分けが実装済（品番台帳: 4レベル / 発注書作成: 3レベル / 発注情報: 2レベル / 工程実績: 2レベル）。MVP は踏襲。**2026-07-27 追記: 実装は AS-IS の 4 カテゴリ + 勤怠（3レベル）の計 5 カテゴリ**（Iteration 30）。詳細: `domain-context/industry/honshu-master-schema.md#7` |
| 工程実績管理権限 | **DB カラムとして保持、UI には出さない**（MVP 対象外機能だが将来拡張のためフィールドは確保）。**2026-07-27 訂正: 実装では「オーナー権限」として利用者マスタ管理・勤怠管理系の判定に使用しており、`/masters/users` で UI 露出済み** |
| 担当属性 | **AS-IS で確認済**。企画担当 / 営業担当 のチェック属性が存在 |
| 監査ログ | **主要トランザクション（品番・発注・マスタ）のみ記録** で確定。スポンサー仮説「証跡」と整合、コストバランス重視 |

### 3.2 検索性

UC-2, UC-3 で品番検索・発注書検索が必要。検索基準（品番・商品名・取引先・日付範囲・状態等）は Phase 3 で詳細化。

### 3.3 排他制御

**ロックなし（Last-Write-Wins）** で確定。同時利用 1-2名のシングルユーザ近似運用と整合する最小実装。複雑なロック機構は MVP では実装しない。

### 3.4 帳票テンプレート

Excel テンプレートのデザインは MVP では既存帳票を踏襲する想定。テンプレートエンジン選定は Phase 4。
